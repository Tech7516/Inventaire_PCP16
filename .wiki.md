# Project Summary

Application web collaborative de gestion d’inventaire des lots PCP16 pour les équipes opérationnelles. Les administrateurs configurent les lots, sous-lots et kits ; les équipes réalisent sur mobile ou desktop des sessions historisées de vérification, d’inventaire et de désinfection.

L’application associe une SPA React à une API FastAPI et une base de données relationnelle. Elle gère les sessions collaboratives, les validations partielles, la persistance cloud des configurations, le suivi des opérations et la consultation de rapports. Les configurations modifiées dans l’interface Admin sont sauvegardées via l’API et rechargées depuis la base de données.

# Project Module Description

- **Administration des lots et sous-lots** : configuration des lots servant à générer les sessions.
- **Gestion des kits** : création et modification des kits SNV, AERV, Accouchement, Membre arraché, Risque biologique renforcé, Biologique et Pharmacie.
- **Persistance des configurations** : sauvegarde des quantités, suppressions et configurations de kits via l’API backend, puis rechargement depuis la base de données.
- **Inventaires** : génération et suivi des inventaires Accouchement, AERV, SNV, DSA, T7 et AMS à partir des configurations cloud.
- **Sessions collaboratives** : création, reprise, navigation et suivi des ensembles à contrôler.
- **Variantes de Lot C** : le sélecteur Lot B propose Alpha, Bravo, Auteuil et Neuilly.
- **Sections consommables Lot C** : les variantes Lot B partagent les sections sac de soin, sac d’O2 et DSA via des alias.
- **Sessions par variante** : plusieurs sessions actives sont possibles pour un lot si les variantes diffèrent ; un doublon sur une même variante renvoie une erreur 409.
- **Sélection persistante** : les variantes utilisées sont grisées et la sélection est conservée entre les navigations.
- **Sous-sections multi-instances** : gestion des cartes Lot B dans les lots parents et des cartes DSA dans le VPS.
- **Anti-doublon DSA réciproque** : une même variante DSA est désactivée dans les sélecteurs Lot B, DSA standalone et VPS.
- **Validation partielle** : sauvegarde et export possibles dès qu’un POM ou au moins un sous-ensemble est vérifié.
- **Vérification des sous-entités** : contrôles enregistrés par sous-entité, instance et variante.
- **Désinfection** : chaque désinfection est enregistrée comme un événement distinct. Seuls les ensembles effectivement vérifiés sont consignés ; un lot parent n’est journalisé que si ses propres sous-ensembles directs ont été vérifiés.
- **Journal et rapports** : historisation, regroupement et calcul des divergences.
- **Journal de désinfection** : cartes repliables regroupées par lot et variantes, avec dernière date, compteur sur douze mois au format X/3 et historique complet.
- **Actions d’historique** : modification de la date et suppression de chaque entrée de désinfection.
- **Déploiement Heroku** : configuration à la racine pour installer les dépendances backend et démarrer l’API avec Uvicorn.

- `app/frontend/src/pages/Admin.tsx` : administration des lots et des kits éditables.

- `app/frontend/src/pages/Inventory.tsx` : affichage des inventaires, application des configurations cloud et journalisation des désinfections.
- `app/frontend/src/pages/SubEntities.tsx` : gestion des instances et variantes, validation partielle et anti-doublon DSA réciproque. Le traitement des désinfections journalise les sous-ensembles vérifiés et ne consigne le lot parent que si ses propres sous-ensembles directs ont été vérifiés.

- `app/frontend/src/pages/Index.tsx` : affichage des lots, sessions actives et variantes persistées ou verrouillées.
- `app/frontend/src/lib/configStore.ts` : appels API centralisés pour charger et sauvegarder les configurations de lots et de kits ; les kits utilisent la route des préférences partagées.

- `app/frontend/src/components/ui/sonner.tsx` : configuration des notifications.
- `app/backend/routers/` : routes de gestion, de session et de consultation.
- `app/backend/data_models/` : schémas des configurations, inventaires, sessions et rapports.
- `app/backend/models/` : entités persistées en base.
- `app/backend/services/` : traitements métier.

# Technology Stack

- **Frontend** : React 18, TypeScript 5.5+, Vite 5, Tailwind CSS, React Router, TanStack React Query, Axios, Zod, React Hook Form, Recharts et Lucide.
- **Composants UI** : shadcn/ui, Radix UI et Accordion.
- **Notifications** : Sonner.
- **Backend** : Python 3.10+, FastAPI, Uvicorn, Pydantic 2, SQLAlchemy 2 asynchrone et Alembic.
- **Runtime de déploiement configuré** : Python 3.12.
- **Base recommandée** : PostgreSQL 12+ avec asyncpg.
- **Base de développement** : SQLite ; MySQL/MariaDB sont supportés par le code mais déconseillés en production.
- **Déploiement optionnel** : Heroku avec Procfile ; Mangum pour AWS Lambda.
- **Dépendances complémentaires** : python-jose, Stripe et OpenAI selon les fonctionnalités activées.
- **Gestionnaires de dépendances** : pip côté backend et pnpm côté frontend.

# Usage

1. Installer les dépendances backend depuis la racine du dépôt :

   ```bash
   pip install -r requirements.txt
   ```

   Il est aussi possible d’installer directement les dépendances backend :

   ```bash
   pip install -r app/backend/requirements.txt
   ```

2. Installer les dépendances frontend :

   ```bash
   cd app/frontend
   pnpm install
   ```

3. Configurer au minimum `DATABASE_URL`, ainsi que `ENVIRONMENT` et `PORT` si nécessaire.

4. Vérifier la syntaxe backend :

   ```bash
   cd app/backend
   python -m py_compile routers/shared_data.py
   python -m py_compile routers/collaborative_inventory.py
   ```

5. Vérifier le lint frontend et construire l’application :

   ```bash
   cd app/frontend
   pnpm run lint
   pnpm run build
   ```

   Le build est généré dans `dist/` et peut être servi par un serveur web ou un CDN avec fallback vers `index.html`.

6. Pour Heroku, les fichiers de configuration à la racine définissent Python 3.12, l’installation des dépendances et la commande de démarrage Uvicorn. Configurer les variables d’environnement et la base de données sur la plateforme avant le déploiement.

7. En production, provisionner PostgreSQL, appliquer les migrations, activer HTTPS, configurer le proxy inverse et vérifier le point de santé.

8. Pour AWS Lambda, activer le mode Lambda et utiliser un pool de connexions sans état via Mangum.

9. Après toute modification des configurations, variantes ou de la journalisation, exécuter le lint et le build frontend.
